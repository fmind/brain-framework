# Troubleshooting

Start inside the intended brain. These commands inspect saved files and local history, without running programs or contacting providers:

```bash
bf --version
bf validate
bf status
```

Read the file, field or program the diagnostic names before retrying. Diagnostics go to stderr and never quote your content.

## A program fails

Failed collection leaves saved records intact. `bf status` marks the program `"failed":true` with its `error`, consecutive `failures` and `log`, such as `logs/calendar.log`. The log can hold provider output: read it locally and never paste it into a public issue. Fix the cause, then rerun the program with `bf collect SENSOR` or `bf run ROUTINE`; updates retry on their own after the failure backoff.

`bf collect SENSOR --dry-run` **executes the sensor** and may contact its provider; `bf update --dry-run` only lists due work. A program that `bf validate` reports as `not an executable regular file` needs `chmod +x`, or an interpreter in its `command`. Behind an interpreter, as in `[uv, run, --no-project, sensors/brief.py]`, validation checks only that the first `sensors/`, `routines/` or `channels/` path among the arguments exists: `is not a regular file or folder` points to a missing file or a typo. `program was killed by SIGKILL` means another process, such as the out-of-memory killer, ended the program.

A snapshot fails with `snapshot would remove N of M records` when it would empty its source, or remove more than half of it and more than 10 records. Check the account, folder and provider response; do not delete stored records to make collection pass. When the removal is intended, accept it once with `bf collect SENSOR --allow-removal`.

## An assistant fails {#a-prompt-fails}

A failed assistant run retains its queue state and any saved answer; its log holds the harness's stderr. To see what the harness receives, add a temporary assistant that reuses the prompt file with `command: [cat]` and no `text`, `inputs`, `outputs` or `schedules`, such as `prompt-check: {prompt: prompts/personal.md, command: [cat]}`, then run `bf run prompt-check --dry-run`, adding `--stdin` with a piped message to fill `{{input}}`: the reply's `text` is the expanded prompt, and nothing is recorded, queued or delivered. Remove that assistant afterwards.

Do not swap the `command` or `text` of an assistant that has pending work, even for a moment. Each job keeps the prompt, harness and output settings it was queued with, and a pending job a worker tries while they differ fails with `assistant configuration changed`; editing `schedules`, `inputs` or `keep` leaves queued jobs runnable, and once a harness has answered, only removing or disabling the assistant or changing an output channel stops its saved answer. Restoring the settings does not resume a failed job: until `bf queue ID --retry` or `--cancel`, it blocks the later jobs of its conversation, or its schedule. Work queued meanwhile keeps the changed settings: it runs with them, delivering whatever that command prints, or fails once you restore them.

| Error or reply                                                  | Cause and fix                                                                                                                                                                                                                                                                                                                                                   |
| --------------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `assistant command must print one JSON object when text is set` | With `text` set, stdout must be one JSON object. Ask the harness for a single JSON result, such as `--output-format json`, not text or a stream of JSON lines; or remove `text` to keep all of stdout as the reply.                                                                                                                                             |
| `assistant reply has no text string at /…`                      | The pointer names no string. Run the harness once by hand with the same output option, list the members of its JSON, then point `text` at the reply, such as `/result` for Claude Code or `/response` for Antigravity.                                                                                                                                          |
| `expanded assistant prompt exceeds 120000 bytes; shorten …`     | The [prompt size limit](limits.md#size-bounds) applies on standard input too, not only to `{{prompt}}` in an argument. Shorten the prompt file or the piped input, and let the harness read evidence with `bf read`. A queued job keeps its template, so only `bf queue ID --cancel` resolves it; a message's job blocks its conversation until then.           |
| `the argument holding the prompt exceeds Linux's 128 KiB limit` | The rest of that argument pushed it over Linux's bound. Shorten it, or drop `{{prompt}}` so the prompt arrives on standard input, if the harness reads it there.                                                                                                                                                                                                |
| `… configuration changed; restore it …`                         | The assistant's prompt, harness or output settings, or the `send` command of a channel its job delivers to, differ from those the job was queued with, or the assistant was removed or disabled. Restore them, then run `bf queue ID --retry`, or abandon the job with `bf queue ID --cancel`. Until then it blocks later jobs of its conversation or schedule. |
| `"status":"skipped"` in a `bf update` reply                     | Without `job`, the active watch dispatcher owns automatic work. With `job`, another process runs that job, or its `skipped` reason says it waits until `bf.yaml` loads. Inspect `bf queue` for failed or uncertain jobs; schedule progress remains independent of direct runs.                                                                                  |
| `program exited with status …`, a sign-in error in the log      | The harness is not signed in for the account and environment running BF. Sign in as that user; a [service](schedule.md#run-watch-as-a-service) or timer gets only the variables its file sets, such as `PATH`, not your shell's.                                                                                                                                |
| The reply says the agent could not run `bf read` or `bf search` | The harness cannot ask for approval without a terminal, or its `--tools` list leaves out `Bash`. Allow those read-only commands in its command, such as Claude Code's `--allowedTools 'Bash(bf read *),Bash(bf search *)'`, or in its permission settings, and keep `Bash` in any `--tools` list.                                                               |
| `program timed out after …s`                                    | Give the harness its own time limit below `timeout`, such as Antigravity's `--print-timeout`, and keep the prompt's task small.                                                                                                                                                                                                                                 |

Inspect `bf queue` for failed or uncertain assistant jobs. A saved answer resumes without rerunning the harness; an interrupted harness needs explicit review before `bf queue ID --retry` because tools might already have acted. Delivery retry sends only the saved answer. See [assistant settings](prompts.md) and [queue recovery](channels.md#queue-and-recovery).

### Queue and channel errors

| Error or reply                                                                                   | Cause and fix                                                                                                                                                                                                                                                                                                                                                                                              |
| ------------------------------------------------------------------------------------------------ | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `PROMPT: cannot read assistant NAME's prompt; …`                                                 | Restore the prompt file or correct `prompt` in `bf.yaml`. The assistant's schedules wait meanwhile and start once it reads.                                                                                                                                                                                                                                                                                |
| `assistant queue is full; …`, `admitted N of M messages`                                         | Unfinished work fills the [queue](channels.md#queue-and-recovery). Retry or cancel the failed and uncertain work `bf queue` lists; a read input catches up at its next poll, and a stream's provider redelivers.                                                                                                                                                                                           |
| `assistant queue lacks answer space for this job; …` or `… for this run, so it was cancelled; …` | Running jobs hold the space: the job starts once they finish. `bf run` cancels its job instead, so run it again then.                                                                                                                                                                                                                                                                                      |
| `assistant NAME needs N MiB of queue space per answer, …`                                        | `bf validate` reports it as `assistants.NAME: an answer with N outputs needs …` before any run. Lower the assistant's `max_bytes` or its outputs ([limits](limits.md#processes-and-logs)), then retry the job.                                                                                                                                                                                             |
| `assistant queue holds unresolved work admitted under this brain's previous path or name; …`     | Also reported by `bf status` after a move or rename: restore the previous path or name, resolve the work with `bf queue`, then move or rename again. A drained queue needs nothing: the next `bf queue` or execution command rebinds it. Collection still works meanwhile.                                                                                                                                 |
| `assistant queue predates this release; …`                                                       | An earlier release created this queue, which `bf status` reports too, and execution refuses it. Follow that upgrade's manual steps in the [changelog](../changelog.md), which resolve its work and update the queue in place; never delete it. Resolving needs the previous release: reinstall it, such as `uv tool install --python 3.14 'brain-framework==19.1.0'`, drain the queue, then upgrade again. |
| `unexpected assistant queue schema; …`                                                           | Another build created this queue, such as a pre-release one, which `bf status` reports too: resolve its work with that build, then move its `queue.sqlite3` aside, as the [v19 upgrade steps](../changelog.md) say.                                                                                                                                                                                        |
| `assistant queue holds an interrupted write; …`                                                  | A BF process was killed while writing the queue. Run `bf queue`, or any execution command, to roll the write back. Keep `queue.sqlite3` and its `-journal` file together and delete neither.                                                                                                                                                                                                               |
| `job is still running; …` or `delivery is still being sent; …`                                   | Another process, such as `bf run`, `bf update` or watch, still runs that attempt. Let it finish or stop that process, then run the command again: an attempt whose process ended is recorded first, so `--retry` or `--cancel` then resolves it.                                                                                                                                                           |
| `stream frame exceeded max_bytes`                                                                | The adapter printed a line longer than `channels.NAME.stream.max_bytes`. Raise a lowered limit, up to the 1 MiB default, or print compact UTF-8, then restart watch: the provider redelivers the message. No valid envelope exceeds 1 MiB: beyond it, fix the adapter's framing.                                                                                                                           |
| `channel NAME: more than 1000 messages fall within one second; …`                                | A read input caught up in parts down to one second and that second still held more than one batch, as when an adapter gives a backlog one timestamp. Give each message its provider time, or read the channel with a `stream` input. The parts admitted before are kept.                                                                                                                                   |
| `assistants.NAME.inputs: unknown channel X`                                                      | Declare `X` under `channels:` or correct the name, here or under `outputs`; `channel X requires MODE` or `requires send` asks for that capability.                                                                                                                                                                                                                                                         |

## Updates do not run

```bash
bf update --dry-run
bf status
```

A sensor or routine runs automatically only when it is enabled, has a nonzero `refresh`, is due and matches the selectors; [timing and health](schedule.md#timing-and-health) gives the rule. The dry run's `manual` list names enabled sensors and routines with `refresh: 0`, and assistants without schedules or inputs. Watch must stay open, in a terminal or as a service, or a timer must be active on a running machine; see [service behavior and host lifecycle](schedule.md#run-watch-as-a-service). Check health on the collecting machine: a teammate's clone shares the records, not the run history.

## Recover the cache or an interrupted write

While an interrupted record write awaits recovery, `bf status` reports `"pending_transaction":true`, a `stale` or `missing` [cache](commands.md#status-sources-and-routines) and a problem naming the command to run. Let active collection finish, then:

```bash
bf build
bf validate
bf status --check
```

`bf build` recovers the interrupted write and rebuilds the cache from the files. Before replacing records, a write keeps hard-link backups of them in `memories/.pending/`. Recovery restores only the files that write changed; keep that folder until it succeeds. `bf collect`, `bf update` and `bf watch` also recover it before writing; search and read never do.

If `bf build` refuses the journal itself, keep what it holds. For `unexpected file in memories/.pending`, move the file it names out of the brain and run `bf build` again. For any other refusal that names `memories/.pending`, such as `invalid memories/.pending manifest`, `duplicate paths in memories/.pending manifest` or a missing or oversized `.before` backup, move the whole `memories/.pending` folder out of the brain, run `bf build` and `bf validate`, then collect the source its manifest names again: each record file is whole, but that collection may be half applied.

The rebuild fills `.bf/index.sqlite.new` beside the live cache and replaces it when complete: searches keep answering meanwhile. A rebuild killed before it finishes leaves that file, which the next search, read or status removes once no build is running. `bf build` exits 1 when its `skipped` count shows unreadable files; `bf validate` names them. A damaged cache is discarded and rebuilt on its own. An exact read that meets an active write returns within about 3 seconds, marked `stale`: retry it for the final content.

## Files

| If you see…                                                                    | What to do                                                                                                                                                                                                                                |
| ------------------------------------------------------------------------------ | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| A record file edited by hand still answers with its old text                   | Collection renames records into place; a file edited in place leaves its folder unchanged, so searches keep the cached copy. Run `bf build`. A skipped record fixed in place, or whose permissions you restore, is read again on its own. |
| A skipped link or special file in `problems`                                   | Replace a link with the file or folder it points to, and a special file with a regular file, inside the brain; BF never follows links.                                                                                                    |
| `unreadable folder` or `inaccessible file or folder`                           | Restore read and search permission, such as with `chmod -R u+rwX memories`, or move the folder out of the brain; the rest of the brain keeps answering.                                                                                   |
| `unreadable file; retried next time`                                           | A read failed, such as on a network or sync mount: the next search, read or status tries the file again. If it persists, check the mount or disk.                                                                                         |
| A file name that is not valid UTF-8, or holds a backslash or control character | Rename the file, shown with escapes such as `\xNN`, as for a Latin-1 name from an old archive.                                                                                                                                            |
| `expected a folder; replace the file with a folder`                            | A file stands where `projects/`, `concepts/`, `actions/` or `memories/` belongs: move it out of the brain, create the folder, then run `bf validate`.                                                                                     |
| `expected a directory; symlinks and special files are not followed`            | Replace the linked folder with a regular one.                                                                                                                                                                                             |
| `note is not UTF-8`                                                            | Convert the named note to UTF-8.                                                                                                                                                                                                          |
| Git conflict markers at the start of a line                                    | Reconcile both revisions: the note stays unsearchable until then, even inside a code block.                                                                                                                                               |

Writes are atomic. A write killed before its rename, by BF or the bf-use guarded-write helper, leaves a `.write-HEX` file beside its target. The next write of a record source removes its own; `bf validate` warns about those in `projects/`, `concepts/` and `actions/` (`an interrupted write left this temporary file; delete it`), and none blocks an action routine. An editor's lock files, named `.#NAME`, are ignored. A file removed during a scan, as by an editor's save, is indexed at the next refresh.

## Report a reproducible problem

Include the BF version, operating system, the failing command with private paths replaced, its exit code, and expected versus observed behavior. Reproduce it with a small fictional note or record; omit private passages, credentials and logs. Use [GitHub issues](https://github.com/fmind/brain-framework/issues) for bugs and the [private reporting instructions](https://github.com/fmind/brain-framework/blob/main/SECURITY.md) for suspected vulnerabilities.
