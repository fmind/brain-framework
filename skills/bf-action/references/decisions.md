# Decisions, intentions and unknowns

Use the sections that the action needs; omit empty sections. Work remains one user-requested session, not a new task engine. Keep durable commitments and unresolved questions in the owning project when they outlive the action.

## Decide and learn

Before a consequential choice, record the chosen option, the useful alternative, the assumption that distinguishes them, evidence refs, an observable expected outcome and a review date or event. Write the expectation before observing the outcome. Do not invent a measurement or numerical confidence.

At review, compare the expectation with an observed result and its evidence. Mark it met, missed or unknown, recording circumstances that changed. Distinguish delivery from impact: a shipped change is not proof it achieved its purpose. Retain a failed prediction; correct the current project conclusion and link the lesson. One outcome does not establish causation. When reviewing a similar decision, inspect both the earlier conditions and its result before reusing it.

For decisions whose old rationale matters, keep a small dated decision note under the action's `outputs/`, with supporting captures in `inputs/`. Correct a mistake explicitly or create a successor with a `supersedes` link; do not silently rewrite the earlier prediction as hindsight. Current project notes still stay short and current. Follow `bf-learn` for evidence capture and claim revision.

## Remember an intention

Put an intention under a stable project heading, with an owner, a condition, the specific refs to inspect, the proposed next action, an expiry and a state: waiting, ready, unknown, resolved or expired. These are words in Markdown, not new core `status` values. For example: "When the documented release contains feature X, review the workaround; expire after the migration is complete."

Check on the next requested project/action review. Start with dates, an explicit status in a named source, or a change from one saved evidence capture. Do not turn arbitrary prose into executable expressions or assume that an absence proves no reply. Conditions needing absence require known collection coverage of the relevant interval; otherwise they remain unknown.

Record the checked evidence revision and result. Re-reading the same revision does not produce a new prompt. A ready intention asks for review, not permission to send, deploy or run a provider. Mark resolved or expired explicitly. Existing deterministic routines may prepare reviews of these notes; this workflow does not install a scheduler or automatically evaluate prose conditions.

## Investigate an unknown

Record the question, which decision it blocks, what has been inspected, what observation would resolve it, and the smallest next investigation. For example: "Does the supported version export this format? Resolve with its current contract and one fixture; older documentation is insufficient."

Prioritize a question by whether its answer could change an active decision. Reuse existing local evidence first. Do not collect, browse or contact someone merely because a note proposes doing so; use the current task's authorization. Mark resolved only with evidence, retain material contradictions, and put unresolved questions into Context when they block its next step.
