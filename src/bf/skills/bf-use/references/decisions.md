# Decisions, intentions and unknowns

Written reasoning inside one requested session or its owning project, not a task engine: use the sections a note needs, and keep commitments and questions that outlive an action in the owning project.

## Decide and learn

Before a consequential choice, record the chosen option, the useful alternative, the assumption that distinguishes them, evidence refs, an observable expected outcome and a review date or event. Write the expectation before observing the outcome; never invent a measurement or a numerical confidence. For example:

```markdown
## Decision {#decision}

Lead with a product explanation, then offer signup. The alternative is a signup-first page. We expect new visitors to describe what the product does without opening the form; see the [project rationale](../../projects/new-website.md#decision).

Review after the next usability session. Outcome: unknown until the session notes are available.
```

At review, compare the expectation with an observed result: met, missed or unknown, with the circumstances that changed. A shipped change is delivery, not proof of impact, and one outcome does not establish causation. Keep a failed prediction, correct the current conclusion and link the lesson; before reusing a similar decision, check its earlier conditions and result.

When an old rationale matters, keep a dated decision note and correct a mistake explicitly or write a successor with a `supersedes` link, as the [evidence guide](evidence.md) shows; never silently rewrite an earlier prediction. Keep the review deadline in the owning project.

## Remember an intention

Put an intention under a stable project heading with an owner, a condition, the refs to inspect, the proposed next action, an expiry and a state in words: waiting, ready, unknown, resolved or expired. For example: "When the documented release contains feature X, review the workaround; expire after the migration is complete."

Check it at the next requested review, from dates, an explicit status in a named source or a change between captures; never turn prose into executable conditions. A condition needing an absence, such as no reply, stays unknown without known collection coverage of the interval. A ready intention asks for review, never permission to send, deploy or run a provider. Mark it resolved or expired explicitly.

## Investigate an unknown

Record the question, the decision it blocks, what was inspected, what would resolve it and the smallest next investigation. For example: "Does the supported version export this format? Resolve with its current contract and one fixture; older documentation is insufficient."

Prioritize questions that could change an active decision and reuse local evidence first. Never collect, browse or contact someone because a note proposes it: only the current request authorizes work. Resolve a question only with evidence, and move blocking questions into the action's Context.
