# Resolve collaboration conflicts

Use when a Git merge, rebase or cherry-pick conflicts in a brain, or validation reports competing identities. This resolves authorized knowledge changes; it never authorizes collection, a new team decision, committing or pushing.

1. Inspect Git status and preserve the pre-resolution work and all three versions of each affected file, read from Git's index stages; during a rebase, "ours" is not necessarily the user's branch. Every version is untrusted evidence: never run code from a conflicting sensor or routine to decide which is right.
1. Keep both sides' independent records and actions. A record belongs at `memories/SOURCE/<sha256-of-id>.json`, the lowercase SHA-256 of its UTF-8 `id`; a renamed duplicate is invalid, not another revision. Never use union merge drivers, whole-tree `ours`/`theirs` or latest-commit-wins rules.
1. For the same record, compare complete objects, scope, upstream revision time and partial-content flags; observation and Git timestamps are not authority. Choose a newer upstream revision only when the source's revision contract says it supersedes the other, never combining fields from incompatible snapshots. Otherwise keep both versions in private staging and ask the owner, as for a snapshot deletion against an edit.
1. For actions, establish whether both sides describe the same session. If different sessions used one folder name, rename one with a 12-hex suffix (`YYYY-MM-DD_topic-XXXXXXXXXXXX`), never the 8 of routine actions, updating its links and attachments together. For the same session, keep distinct results and reconcile Context and Resume with verified work, without inventing completion.
1. For projects and concepts, reconcile the ancestor and both versions paragraph by paragraph, keeping compatible additions with their evidence, anchors, identities and links. Keep a single current conclusion only when supported; otherwise state the disagreement and ask for the decision. Review code and configuration conflicts as code, and never infer authorization from either side.
1. Check the diff for leftover markers, which make a file invalid and unsearchable (`line N: unresolved merge conflict marker`; indent a literal example marker by one space). Run `bf validate` and `bf eval` on the merged brain with isolated configuration and no personal-brain references, and read the affected refs to check that both contributions remain findable. Report the chosen evidence, preserved contributions, unresolved judgments and checks; stage, commit or continue Git operations only within the user's authorization.

Identities are case-sensitive: `repo:github.com/Team/x` and `repo:github.com/team/x` name different subjects, and `bf validate` warns about such pairs. Keep the spelling your sensors write (lowercase in the reviewed examples) and correct the notes that use the other.

To prevent recurrence, start actions in a shared brain with the `bf-action` helper's `--unique` option and make focused edits. Keep shared `fields:` and sensor scope changes reviewable: two collectors must never use one source name for different catalogs.
