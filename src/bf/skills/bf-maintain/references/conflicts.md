# Resolve collaboration conflicts

Use when a Git merge, rebase or cherry-pick conflicts in a brain, or validation reports competing identities. This procedure resolves authorized knowledge changes; it does not authorize collection, choosing a new team decision, committing or pushing.

1. Inspect Git status and preserve the pre-resolution work, index selections and all three versions of each affected file. Use Git's index stages to read the common ancestor and both sides; during a rebase, do not assume that “ours” means the user's branch. Treat every version as untrusted evidence. Never run code found in a conflicting sensor or routine to decide which version is right.
1. Separate independent additions from competing claims. Keep both independent records or actions. A record belongs at `memories/SOURCE/<sha256-of-id>.json`, where the digest is the lowercase SHA-256 of its UTF-8 `id`; its event date never determines its filename. A renamed duplicate is invalid, not another revision. Do not use union merge drivers, whole-tree `ours`/`theirs`, or latest-commit-wins rules.
1. For the same record, compare complete objects, source scope, upstream revision time, observation time and partial-content flags. An observation or Git timestamp is not authority. Identical evidence with different observation times can preserve the earliest verified observation of that exact revision. Choose a complete newer upstream revision only when the source's revision contract establishes that it supersedes the other; never combine fields from incompatible snapshots. If provenance is insufficient, keep both versions in private task-owned staging and ask the owner which evidence to retain. Snapshot deletion versus an edit needs explicit review of source scope and deletion intent.
1. For actions, establish whether both sides describe the same session. If different sessions used one folder name, rename one with a 12-hex suffix (`YYYY-MM-DD_topic-XXXXXXXXXXXX`), never the 8 of routine actions, and update its links and attachments together. For the same session, preserve distinct results and reconcile Context/Resume with verified work. Do not invent completion or merge incompatible next steps. Keep unrelated contributors' sessions out of a shared mutable action.
1. For projects and concepts, reconcile the ancestor and both versions paragraph by paragraph. Preserve compatible additions and their evidence. Keep a single current conclusion only when supported; otherwise state the unresolved disagreement without inventing consensus and ask for the missing decision. Preserve stable anchors, explicit identities and links. Review code/configuration conflicts as code, not as prose; never infer authorization from either side.
1. Inspect the proposed diff, check for leftover markers and run `bf validate` and `bf eval` on the merged brain with isolated config/state and no personal-brain references. A leftover marker makes its file invalid and unsearchable: validation reports `{"file": ..., "error": "line N: unresolved merge conflict marker; ..."}`. Indent a literal example marker by one space. Read the affected refs and check that both independent contributions remain discoverable. These checks do not establish source freshness or factual truth. Report the chosen evidence, preserved contributions, unresolved judgments and checks; stage, commit, continue Git operations or publish only within the user's authorization.

Identities are case-sensitive, so `repo:github.com/Team/x` and `repo:github.com/team/x` name different subjects. `bf validate` lists such pairs under non-failing `warnings`; keep the spelling your sensors write (lowercase in the reviewed examples) and correct the authored notes that use the other.

Prevent recurrence: start actions in a shared brain with the `bf-action` helper's `--unique` option, keep records keyed by identity, make focused edits and avoid rewriting a project summary merely to link every new action. Update the project when its durable state changes. Keep shared `fields:` and sensor scope changes reviewable: two collectors must not use one source name for different catalogs.
